현재 plan을 기반으로 작업을 단계별로 분리합니다.

## 시작 전 필수 단계: Git Branch 생성

step 목록 출력 전에 반드시 해당 작업에 적합한 git branch를 생성합니다.

1. plan 내용을 파악하여 작업 이름을 kebab-case로 추출
2. `git checkout -b <branch-name>` 실행 — 생성과 동시에 해당 브랜치로 전환
3. 브랜치 생성 및 전환 완료를 사용자에게 알린 후 step 목록 출력

브랜치 이름 예시: `feat/user-auth`, `fix/login-redirect`, `refactor/api-layer`

## plan 참조

`docs/plan/` 디렉토리에서 가장 최근 파일을 읽어 plan 내용을 파악합니다.
파일이 없으면 현재 대화 컨텍스트의 plan을 사용합니다.

## 실행 모드

$ARGUMENTS가 `auto`이면: 각 step을 사용자 확인 없이 순서대로 자동 구현합니다.
그 외(기본값): step 목록을 출력한 후, 구현 시 **step 하나가 완료될 때마다 반드시 멈추고** 사용자의 확인("다음 step 진행해줘" 등)을 기다립니다. 사용자가 명시적으로 다음 step을 요청하기 전까지 절대 자동으로 진행하지 않습니다.

사용자 피드백이 현재 step과 무관한 새 작업 지시처럼 보이면, "현재 step과 다른 작업으로 보입니다. `/my-pivot [작업 설명]`으로 전환하시겠습니까?"라고 안내합니다.

## 분해 방식: 수직으로 자르기

레이어별로 자르지 말고, **한 번에 하나의 완결된 기능 경로**를 만듭니다.

```
나쁨 (수평 분해)              좋음 (수직 분해)
Step 1: 스키마 전부           Step 1: 목록 조회 (쿼리 + 훅 + 목록 UI)
Step 2: API 전부              Step 2: 항목 생성 (뮤테이션 + 폼 UI)
Step 3: UI 전부               Step 3: 항목 수정 (뮤테이션 + 편집 UI)
Step 4: 연결                  Step 4: 항목 삭제 (뮤테이션 + 확인 UI)
```

수평 분해는 마지막 "연결" step에서 모든 문제가 한꺼번에 터집니다. 수직 분해는 각 step이 끝날 때마다 실제로 동작하는 기능이 하나씩 늘어납니다.

**불확실한 것부터**: 기술적으로 검증 안 된 부분(외부 연동, 새 라이브러리, 성능이 걱정되는 지점)이 있으면 그것을 Step 1로 올립니다. 여기서 막히면 나머지 설계가 통째로 바뀌기 때문입니다.

## Step 크기 기준

| 크기 | 파일 수 | 판단 |
|------|--------|------|
| 작음 | 1-2개 | 좋음 |
| 보통 | 3-5개 | 좋음 |
| 큼 | 6개 이상 | **더 쪼갤 것** |

아래에 하나라도 해당하면 step을 더 쪼갭니다:

- 완료 기준을 3줄 이내로 못 쓰겠다
- step 이름에 "그리고"가 들어간다 (사실상 두 개의 작업)
- 서로 독립적인 영역 두 곳을 건드린다

## 각 Step 형식

---
**Step N: [작업 이름]**
- **목표**: 이 단계에서 완성되는 것
- **핵심 개념**: 이 작업을 통해 배울 수 있는 패턴·개념
- **작업 내용**: 구체적인 구현 항목 (체크리스트)
- **예상 복잡도**: 낮음 / 보통 / 높음
- **대상 파일**: 변경될 파일 경로 (예상 크기 판단용)
- **완료 기준**: 이 단계가 끝났다고 판단하는 기준
- **검증 방법**: 완료를 확인할 구체적 명령 또는 동작 (예: `npx tsc --noEmit` 통과 + 목록 화면에 항목 표시)
- **커밋 시점**: 즉시 커밋 권장 / Step N+1과 함께 커밋 권장 — 이유 한 줄
---

## 구현 중 스코프 규율

각 step을 구현할 때 **그 step이 요구하는 것만** 건드립니다.

하지 않을 것:
- 지나가다 본 인접 코드 "정리"
- 수정하지 않는 파일의 import 정돈
- 이해 못 한 주석 삭제
- plan에 없는데 "있으면 좋을 것 같은" 기능 추가

개선할 게 눈에 띄면 고치지 말고 기록만 합니다:

```
발견했지만 이번엔 손대지 않음:
- src/utils/format.ts에 미사용 import (이번 작업과 무관)
- 인증 미들웨어 오류 메시지 개선 여지 (별도 작업)
→ 별도 step으로 추가할까요?
```

또 하나: 추상화는 **세 번째 사용처가 생겼을 때** 만듭니다. 비슷한 코드 세 줄이 섣부른 추상화보다 낫습니다.

## step 완료 시 검증

각 step 구현이 끝나면 사용자 확인을 받기 전에 아래를 실행합니다:

```bash
npx tsc --noEmit
```

프로젝트에 테스트·빌드 스크립트가 있으면 함께 실행합니다. 실패하면 다음 step으로 넘어가지 않고 `/my-debug`로 원인을 파악합니다.

> 직전에 성공한 검증 명령은 코드가 바뀌지 않았다면 다시 실행하지 않습니다.

## step 완료 시 마지막 문장

step 구현이 끝나고 사용자 확인을 기다릴 때, 반드시 마지막 문장으로 커밋 권장 시점을 안내합니다.

- 즉시 커밋이 권장될 때: "이 step은 독립적인 단위이므로 `/my-commit`으로 커밋 후 다음 step을 진행하는 것을 권장합니다."
- 다음 step과 묶는 것이 권장될 때: "이 step은 다음 Step N+1과 논리적으로 연결되므로 함께 완료 후 커밋하는 것을 권장합니다."

## 분해 원칙

- 각 step은 독립적으로 커밋 가능한 단위
- 하나의 step에서 하나의 핵심 개념만 다룰 것
- GraphQL, 컴포넌트, 상태관리 등을 혼합하지 말고 분리
- 각 step 완료 후 앱이 동작 가능한 상태를 유지
- 리팩터링과 기능 추가를 한 step에 섞지 않을 것 — 둘 다 리뷰하기 어려워짐

## step 목록 출력 후 안내

step 목록 출력이 끝나면 반드시 아래 문장을 추가합니다:

> step 방향이나 기술 스택을 바꾸고 싶다면 `/my-refine [피드백]`으로 수정할 수 있습니다.
