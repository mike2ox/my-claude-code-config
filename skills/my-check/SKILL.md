작업 완료 후 품질 검사를 두 단계로 실행합니다.

## 1단계: 자동 검증 (직접 실행)

```bash
npx tsc --noEmit
```

프로젝트에 아래 스크립트가 있으면 함께 실행합니다:

```bash
npm run lint
npm test
npm run build
```

오류가 있으면 모두 수정한 후 2단계로 진행합니다. 원인이 불분명한 실패는 `/my-debug`로 넘깁니다.

## 2단계: 5축 리뷰 (Agent 위임)

1단계가 모두 통과했을 때만 실행합니다.

subagent_type을 code-reviewer로 지정하여 Agent tool을 호출하세요. 파라미터:
- description: "변경사항 5축 코드 리뷰"
- prompt: 아래 내용 전달

---
현재 브랜치의 변경사항을 5개 축으로 리뷰합니다.

`git diff main...HEAD`와 관련 파일을 읽어 변경 범위를 파악하세요.

### 1. 정확성
- 의도한 대로 동작하는가? plan의 완료 기준을 충족하는가?
- 엣지 케이스 처리 여부 (null, 빈 배열, 경계값)
- 에러 경로 처리 여부 (성공 경로만 다루지 않았는가)
- off-by-one, 경쟁 조건, 상태 불일치

### 2. 가독성과 단순함
- 이름이 프로젝트 관례와 일관되고 설명적인가 (`temp`, `data` 같은 맥락 없는 이름 금지)
- 제어 흐름이 단순한가 (중첩 삼항, 깊은 콜백 회피)
- **추상화가 그 복잡도만큼 값을 하는가** — 세 번째 사용처가 생기기 전엔 일반화하지 않음
- 죽은 코드 흔적 — 미사용 변수, 하위호환 임시 코드, `// 제거됨` 주석
- **무관한 흐름에 조건문이 덧붙었는가** — 이건 사소한 지적이 아니라 설계 신호. 별도 헬퍼나 상태로 분리할 것

### 3. 구조
- 기존 패턴을 따르는가? 새 패턴이라면 정당한 이유가 있는가
- 중복 코드가 공유되어야 하는가
- **기능 전용 로직이 공용 모듈로 새어나갔는가** — 해당 개념을 소유한 레이어에 둘 것
- 타입 경계가 명시적인가 — 불필요한 `any`/`unknown`/캐스팅, 불명확한 규칙을 덮는 조용한 기본값

### 4. 성능
- 불필요한 re-render — useMemo, useCallback 적용 가능 지점
- GraphQL 쿼리 — 불필요한 필드 요청, fragment 재사용 기회
- N+1 쿼리 패턴, 페이지네이션 누락
- 번들 크기 — dynamic import 적용 가능한 큰 컴포넌트

### 5. 보안·접근성
- 사용자 입력 검증 여부, 외부 데이터를 신뢰하지 않는가
- 비밀값이 코드·로그에 노출되지 않는가
- aria 속성, 키보드 내비게이션 누락 여부

### 출력 규칙

각 항목에 반드시 아래 라벨을 붙입니다:

| 라벨 | 의미 |
|------|------|
| **필수** | 머지 전 반드시 수정 (버그, 보안, 타입 오류) |
| **권장** | 고치면 확실히 나아짐 (구조, 성능) |
| **제안** | 선택 사항 |
| **참고** | 조치 불필요, 맥락 공유용 |

**중요한 것부터 순서대로** 나열합니다. 정확성·보안 → 구조 문제 → 나머지. 사소한 스타일 지적 열 개 밑에 진짜 문제를 묻지 마세요. 구조 문제 1개와 스타일 10개가 있다면, 그 구조 문제가 리뷰의 전부입니다.

각 항목에 파일 경로와 라인 번호를 포함하고, 문제만 지적하지 말고 **어떻게 고칠지**를 함께 제시하세요.

발견이 없는 축은 "발견 없음"으로 명시합니다. 코드 수정은 하지 않습니다.
---

## 3단계: 적용

에이전트 결과를 받은 후:

1. **필수** 항목은 이유를 설명하고 바로 수정
2. **권장**·**제안** 항목은 각각 "적용할까요?"를 사용자에게 확인하고 승인된 것만 수정
3. 수정 후 1단계 검증을 다시 실행

## 4단계: 죽은 코드 점검

리팩터링이나 교체 작업이 있었다면, 이제 참조되지 않는 코드가 있는지 확인합니다.

```
더 이상 사용되지 않는 것:
- formatLegacyDate() — formatDate()로 대체됨
- OldTaskCard 컴포넌트 — TaskCard로 대체됨
→ 제거할까요?
```

확실하지 않으면 지우지 말고 물어봅니다. 다만 죽은 코드를 그대로 남겨두지도 않습니다.

## 변경 크기 점검

리뷰 결과 보고 시 변경 규모를 함께 알립니다.

| 변경 라인 | 판단 |
|----------|------|
| ~100줄 | 좋음 |
| ~300줄 | 단일 논리 변경이면 허용 |
| 1000줄+ | **너무 큼 — 나눌 것 권장** |

한 파일이 1000줄을 넘어가고 있다면, 더 쌓기 전에 분리를 먼저 제안합니다.
